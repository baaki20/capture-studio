# P3 spike S8 — Wayland repeat prompt (PARTIAL GO)

Run on 2026-11-08 on the dev machine: GNOME on Wayland, ScreenCast portal v5 (`AvailableSourceTypes` 7,
`AvailableCursorModes` 7), Electron 45.0.0 running as a native Wayland client with
`WebRTCPipeWireCapturer`. Harness: `spikes/s8/` (throwaway). A step that returns in under 1.5 s had
no human click; the frame statistics show real screen content (mean and spread of luma).

| Launch | Step | Time | Result |
|---|---|---|---|
| 1 | `desktopCapturer.getSources` | 8.9 s | Portal dialog, source `screen:1:0:s` |
| 1 | `getUserMedia` with that id | 10 ms | Frames |
| 1 | `getUserMedia` with the same id again, after the first track stopped | 54 ms | Frames, **no dialog** |
| 1 | `getSources` again | 4.1 s | **Dialog again**, new id |
| 2 | `getUserMedia` with the id from launch 1 | 10–37 ms | Stream opens but delivers **no frames** (one run gave a single placeholder frame) |
| 2, 4, 5 | Same id again, after 20–30 s idle | 3–9 ms | Real frames (≈ 40 per 1.5 s, same picture statistics as the first open), **no dialog** |

Findings:
- **Confirmed:** within one app process, opening the *same* desktop source id again needs no portal
  dialog, also after the previous track has stopped and after idle time. Calling `getSources` again
  always shows the dialog.
- **Confirmed:** across app launches the old id does not work (no frames, no error), so the app
  must not reuse an id from a previous launch.
- **Inferred:** this is WebRTC's in-process restore-token store (the Electron binary contains the
  portal's `restore_token` and `persist_mode` strings): the second open starts a new portal session
  with the token from the first. The token never reaches the app, so it cannot be saved.
- **Not checked:** whether GNOME's "screen is being shared" indicator stays on between recordings.
  The PipeWire dump filter in the harness did not match GNOME's stream node names; check by eye
  during step 8.

Decision for step 8:
- **Go** for "no dialog from the second recording on, while the app runs": keep the chosen source id
  in memory (never on disk), reuse it for the next recording, and detect a dead id (no first frame
  within 2 s) to fall back to `getSources`. Diagnostics gets "Choose the screen again", which drops
  the id. Changing the capture mode or monitor also drops it.
- **No-go** for "no dialog after a restart": that needs our own D-Bus portal session with
  `persist_mode=2` and the helper decoding the PipeWire node, which plan D10 rules out. The first
  recording after each launch still shows the dialog; risk 4 stays documented.
- Acceptance (g) ("a second recording needs no dialog") is met within one app run.
